# LLM Output Contracts

This is the application adapter contract, not a general API-provider reference.
Canonical types: `ResearchCardDraft` in `models.py` and `CardsEnvelope` in
`llm/openai_client.py`. Model selection and costs belong in the [runtime guide](runtime-guide.md).

## Structured cards

The adapter parses a `CardsEnvelope` containing at least one card. Example:

~~~json
{
  "cards": [
    {
      "type": "identification",
      "title": "Parallel trends assumption",
      "content": "The design assumes parallel untreated outcome trends; review the cited passage.",
      "chunk_ordinal": 0,
      "page_start": 2,
      "page_end": 3,
      "section": "Identification",
      "tags": ["difference-in-differences"],
      "claim_kind": "author_claim"
    }
  ]
}
~~~

| Draft field | Constraint |
| --- | --- |
| `type` | One of the card types below |
| `title`, `content` | Nonempty strings; this is not a semantic truth check |
| `chunk_ordinal` | Nullable integer ≥ 0; non-null references must exist in the stored chunks |
| `page_start`, `page_end` | Nullable integers ≥ 1 |
| `section` | Nullable string |
| `tags` | List of strings, default empty |
| `claim_kind` | One of the four values below |

Unknown fields inside a card draft are forbidden. The application model has defaults for optional
fields; the provider-facing structured schema is generated by the SDK, not maintained as a
second hand-written schema here. Current field validation does not enforce every cross-field
rule, such as page-end being after page-start.

Card types: `research-question`, `contribution`, `data`, `identification`, `assumption`,
`econometric-specification`, `result`, `robustness`, `heterogeneity`, `mechanism`,
`limitation`, `external-validity`, `method`.

Claim kinds: `author_claim`, `evidence`, `interpretation`, `critical_assessment`.

## Validation and storage

Prompts request uncertainty, source-linked claims and a distinction between correlation and
causation. These instructions are not guarantees. Refusal, missing structured output, invalid
fields or unknown chunk references fail the generation attempt.

The repository validates chunk references before replacing cards. It resolves ordinals to stored
chunk IDs and can fill missing page/section metadata from the source. The public card response
adds persistence fields; it is not the raw model draft.

Only a successful generation replaces current cards. Failed attempts are retained with errors,
and previous cards survive. Reparse alone never updates generated card text.

## Deep reads

Deep reads use an ordinary model text response, not `CardsEnvelope`. The adapter requires nonempty
text and returns it as report Markdown. The application wraps it with `id`, `paper_id`, `focus`
and `created_at` in `DeepReadResult`.

Prompts ask for economics-specific analysis and `[chunk N]` references. There is no strict
section schema or semantic proof that each citation supports the generated claim.
The UI only creates reference links for known chunks and uses its safe Markdown/math renderer.
Always review important claims against the original PDF.

## Telemetry

Adapter results carry domain output plus metrics; provider metrics are not fields the model must
generate in its prose/JSON. The service persists usage, status and price snapshots separately.
See [data model](data-model.md) and [API usage routes](api-contracts.md).
