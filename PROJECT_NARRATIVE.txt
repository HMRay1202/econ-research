Econ Research 项目完整叙述

更新日期：2026-09-02。本文描述当前待提交版本；发布与验证状态以 docs/release-readiness.md 为准。

一、项目定位

Econ Research 是一个本地优先的经济学论文研究工作台。它把 PDF 论文转换为可长期保存的原始资料、带章节和页码来源信息的可检索文本块、面向经济学研究的结构化研究卡片，以及针对单篇论文的深度阅读报告。

项目的核心目标不是生成普通摘要，而是形成可追溯、可复查、可重新生成的研究知识。原始 PDF 始终是权威来源；解析 Markdown、source chunks、研究卡片和深读报告都属于派生内容，不能替代或覆盖原始 PDF。

Phase 1 已完成。项目明确不包含云端部署、用户账户、向量数据库、知识图谱、Zotero、React、多 LLM Provider、LangChain、Celery、Docker 编排和多 agent 工作流等功能。

二、总体架构

系统采用单一业务服务层：

Typer CLI -----------+
                     |
FastAPI API ---------+--> ResearchService
                     |        |
本地浏览器 ----------+        +--> Parser / Docling
                              +--> ResearchLLM / OpenAI
                              +--> SQLiteRepository

核心约束如下：

- CLI 和 HTTP handler 必须调用 ResearchService。
- LLM 调用必须经过 ResearchLLM。
- 数据库读写必须经过 SQLiteRepository。
- 浏览器只能调用已文档化的 /api/* 路由。
- 浏览器不能访问 SQLite、.env、运行时文件路径或 OpenAI Key。
- 不能把 data/ 整体挂载为公共静态目录。
- 浏览器可见 API 变化必须保持 additive，并更新 docs/api-contracts.md 与测试。

主要代码：

- src/econ_research/models.py：Pydantic 领域模型与 API 数据结构。
- src/econ_research/service.py：全部主要业务流程。
- src/econ_research/api.py：FastAPI 应用与 HTTP 路由。
- src/econ_research/cli.py：research 命令行入口。
- src/econ_research/bootstrap.py：配置、Repository、Parser 和 LLM 的组装。
- src/econ_research/config.py：环境变量和运行目录配置。
- src/econ_research/db/repository.py：SQLite 持久化和搜索边界。
- src/econ_research/db/schema.sql：数据库表、索引和 FTS5 schema。
- src/econ_research/parsing/docling_parser.py：PDF 解析和分块。
- src/econ_research/parsing/formula_ocr.py：可选局部公式 OCR。
- src/econ_research/parsing/paddle_process.py / paddle_worker.py：Windows GPU 公式识别的独立进程与协议。
- scripts/setup_runtime.py / runtime_policy.py：跨平台、硬件感知的运行库安装与无模型检查。
- src/econ_research/llm/openai_client.py：OpenAI 适配器。
- src/econ_research/llm/prompts.py：卡片和深读 prompt。
- src/econ_research/llm/telemetry.py：token、耗时和成本遥测。
- src/econ_research/web/：原生 HTML、CSS 和 JavaScript 本地前端。

三、PDF 导入流程

ResearchService.ingest() 负责完整导入流程：

1. 验证文件存在、扩展名为 .pdf，且文件头为 %PDF-。
2. 计算源文件 SHA-256。
3. 检查精确重复或正在处理的相同文件。
4. 将原始 PDF 保存为 data/originals/{paper_id}.pdf。
5. 使用 Docling 解析 PDF。
6. 导出标准化 Markdown。
7. 生成带章节、页码和稳定 ordinal 的 source chunks。
8. 保存论文、文本块，并建立 SQLite FTS5 索引。
9. 通过 ResearchLLM 生成研究卡片。
10. 成功后将论文标记为 ready。

运行时目录默认如下：

data/
├── originals/   原始 PDF
├── parsed/      解析 Markdown
├── generated/   深读报告
├── incoming/    上传队列临时文件
├── models/      可选公式 OCR 模型资产
└── research.db  SQLite 数据库

这些内容属于运行时数据，不应提交到 Git。原始 PDF 从不被派生输出覆盖。

四、重复检测与失败恢复

精确重复通过 PDF SHA-256 判断。不同 PDF 还会根据 DOI、规范化解析文本哈希和标题判断可能重复。可能重复只作为提示返回，系统不会自动合并或覆盖论文。

如果相同 PDF 已成功导入，系统返回已有论文；如果仍处于 processing，则拒绝重复并行处理；如果之前失败，可以重新开始该论文的导入。

解析或卡片生成失败时，论文记录会保留并标记为 failed，同时保存诊断错误。解析结果不会因为卡片失败而被删除，之后可以只重试卡片生成。

五、PDF 解析实现

DoclingParser 使用 Docling 完成页面布局解析、文本提取、章节识别、页码来源追踪和 Markdown 导出。ParsedDocument 包含标题、作者、年份、Markdown、ParsedChunk 列表以及公式处理统计。

每个 source chunk 通常包含：

- ordinal
- text
- section
- page_start
- page_end

优先使用 Docling 产生的文本块。如果 Docling 没有可用文本块，则使用 Markdown 备用分块。备用分块保留章节和 ordinal，并对过大的文本段按约 6000 字符拆分。

标题处理采用保守策略：优先使用 PDF metadata title，其次从 Markdown 标题推断。如果发现旧 PDF 字体映射明显损坏，只对第一页使用 OCR 修复标题、作者和年份，不用整篇 OCR 替换正文。

六、表格与公式 OCR

Docling 识别到的表格不会只存在于完整 Markdown 导出中。解析器会通过文档的有序顶层 item 迭代器提取表格，并将表格序列化为 Markdown 表格块，放回其与周围正文相同的阅读顺序中。表格会保留页码范围，并进入 source chunks、FTS5 搜索、卡片 prompt、深读 prompt 和前端 source-chunk 查看器。单个表格在必要时可以超过普通文本 chunk 的字符限制，但不会被拆散。

公式处理由 formula_ocr.py 负责。流程是：

1. Docling 识别公式区域。
2. 根据页面坐标裁剪局部公式图片。
3. 只将公式 crop 交给 PaddleOCR Formula。
4. 返回并规范化 LaTeX。
5. 替换 Markdown 中对应公式。
6. 如果第一次识别结果未通过 LaTeX 安全校验，会依次使用更大边距和更高分辨率的 crop 重试。
7. 如果所有重试仍然失败，但 OCR 返回了原始字符串，则将其保存为 fenced `latex` 代码块；该内容不会被 KaTeX 渲染，但会保留在 Markdown、source chunks 和 LLM 输入中。
8. 如果没有任何 OCR 文本，则保存可见的页面错误标记；如果依赖不可用，则保留 Docling 原文或占位内容。

系统在论文记录中保存发现数、识别数、回退数、处理状态和有界错误信息。公式 OCR 是可选功能，不是 OpenAI 调用，也不产生 OpenAI 费用。未验证的 OCR 结果不会被当作可执行或可渲染数学，但仍可用于搜索和 LLM 上下文。缺少依赖或单个公式失败不应使整篇论文导入失败。

安装硬件对应的公式依赖（先停止服务）：

conda run -n econ-research python scripts/setup_runtime.py --install

Windows 支持的 NVIDIA 配置将 CUDA Torch 留在 econ-research，在该环境下的 paddle-worker 独立虚拟环境安装 Paddle GPU，不让两套 cuDNN DLL 进入同一进程。CPU Windows 和 macOS 使用 CPU Paddle；macOS Torch 可选择 MPS。安装和启动检查只验证运行库与小型运算，不下载模型；缺失模型在实际识别时首次下载。独立 worker 在单篇论文内复用模型，识别超时为 300 秒，解析结束后关闭。旧的 .[formula-gpu] extra 不是 Windows 推荐安装方式，不能将 CPU/GPU Paddle 混装。

ECON_RESEARCH_FORMULA_ENRICHMENT=true 对应旧的实验性 CodeFormula 路径，默认关闭。ECON_RESEARCH_PADDLE_FORMULA_OCR=false 可以显式关闭 PaddleOCR Formula。

七、研究卡片

研究卡片通过 ResearchLLM.generate_cards() 生成。卡片类型包括：

- research-question
- contribution
- data
- identification
- assumption
- econometric-specification
- result
- robustness
- heterogeneity
- mechanism
- limitation
- external-validity
- method

每张卡片还区分以下 claim kind：

- author_claim
- evidence
- interpretation
- critical_assessment

卡片包含类型、标题、内容、标签、chunk ordinal、章节、页码和 claim kind。Prompt 要求模型关注因果识别、内生性、IV、DiD、事件研究、RDD、固定效应、并行趋势、稳健性、异质性、机制以及内外部有效性，同时不能把相关性默认为因果关系，也不能虚构页码、假设或实证结果。

默认卡片模型为 gpt-5.6-luna，reasoning effort 为 low。成功生成会替换当前卡片集，但每次生成尝试都会保留在 card_generations 表中。

八、深度阅读

ResearchService.deep_read() 只加载选定论文的 source chunks，并可接收用户提供的 focus，然后调用 LLM，保存完整报告和 Markdown 文件。

深读分析研究问题、贡献、数据、识别策略、识别假设、计量模型、主结果、稳健性、异质性、机制、识别威胁、内部有效性、外部有效性和局限性。报告应尽可能使用 [chunk N] 引用来源。

默认深读模型为 gpt-5.6-terra，reasoning effort 为 medium。深读只使用单篇论文，不引入跨论文上下文；它不是向量 RAG 系统。

九、LLM 与使用遥测

所有真实 LLM 调用通过 ResearchLLM 抽象，并由 OpenAIResearchLLM 实现。每次调用记录：

- provider request ID
- 模型和 reasoning effort
- 输入、缓存输入、cache write、输出、reasoning 和总 token
- 调用耗时
- 成功或失败状态
- 错误信息
- 调用开始和结束时间
- 调用时的价格快照
- 估算美元成本

价格快照随调用保存，因此未来修改价格表不会改变历史成本估算。离线测试使用 test doubles，默认不调用 OpenAI，也不产生费用。

十、数据库结构

主要表包括：

- papers：论文主记录、状态、路径、元数据、归档和公式诊断。
- chunks：论文拥有的有序 source chunks。
- cards：当前研究卡片及其来源 provenance。
- card_generations：每次卡片生成尝试及结果。
- deep_reads：深读报告和 focus。
- llm_calls：LLM 调用、token、耗时和估算费用。
- ingest_jobs：上传任务和处理进度。
- ingest_job_events：上传任务的详细后端事件。
- formula_attempts：每个公式的裁剪策略、原始和规范化输出、校验状态及失败裁剪图引用。
- paper_sources：源文件版本和重复检测信息。
- search_index：SQLite FTS5 搜索虚拟表。

数据库初始化使用增量的 CREATE TABLE IF NOT EXISTS。禁止删除运行时数据库来解决 schema 变化；未来不兼容变化必须通过显式 migration 完成。外键在显式永久 purge 时级联删除关联记录，普通软归档不会删除历史。

十一、上传队列

浏览器通过 POST /api/uploads 创建上传任务。任务返回 202，文件先存入 data/incoming/，之后由 ResearchService 内部单线程 ThreadPoolExecutor 处理。

任务阶段包括 queued、validating、preparing_parser、parsing、formula_detection、formula_ocr、chunking、indexing、generating_cards、saving 和 completed。

前端每 2 秒轮询任务状态，服务端每 10 秒记录 liveness heartbeat。阶段和事件会持久化到 SQLite，因此页面刷新后可以恢复进度。处理完成后临时上传文件会被删除。该系统没有引入 Celery 或其他外部任务基础设施。

服务重启后，遗留 queued/running 任务会标记为 interrupted，不会自动重放可能计费的工作。未完成的卡片生成会标记失败，但旧的已完成卡片仍保留可用。

十三、本地前端

前端位于 src/econ_research/web/，由 index.html、styles.css、app.js 和固定版本 vendor 资源组成。它使用原生 HTML、CSS 和 JavaScript，不引入 Node 构建系统或前端框架。

已实现的前端能力包括：多文件上传、任务进度、刷新恢复、论文列表、卡片浏览和过滤、source chunk 查看、FTS5 搜索、原始 PDF 和 Markdown 下载、深读生成与历史、使用统计、标题和年份编辑、归档恢复、永久删除、公式重新解析以及卡片重生成。

普通 UI 字符串和卡片标题使用 textContent；卡片正文、深读和 source chunk 通过共享的 Marked、DOMPurify 和 KaTeX 路径渲染。无法渲染的公式显示为未验证 LaTeX 代码及原文核对提示，不直接展示 KaTeX 错误。脚本、事件属性、iframe、SVG、图片和嵌入媒体不会被渲染。报告中的 [chunk N] 只有在该 chunk 属于当前论文时才会变成可点击按钮。

十四、重解析

research reparse PAPER_ID 或 POST /api/papers/{paper_id}/reparse 会从受控目录读取原始 PDF，使用当前解析器更新 Markdown、按阅读顺序排列的 source chunks（包括表格）、章节、页码 provenance 和公式 OCR 结果。

重解析不会修改原始 PDF，不调用 LLM，不自动生成卡片，也不修改已有卡片文本或深读报告。已有卡片会尽可能按原有 chunk ordinal 重新连接到新 chunks；新的表格或公式内容首先进入解析结果，只有显式卡片重生成后才会进入卡片 prompt。若修订后的文本需要进入卡片，用户必须显式执行卡片重新生成，因为那是可能计费的 LLM 操作。

十五、归档与删除

DELETE /api/papers/{paper_id} 是软归档，只设置 archived_at，并保留 PDF、Markdown、卡片、深读报告和调用历史。POST /restore 可以恢复。

DELETE /api/papers/{paper_id}/purge 才是永久删除。Service 先验证目标路径，再清理公式诊断目录、受控 PDF、Markdown 和深读报告，全部文件清理成功后才删除数据库记录。Windows 因只读属性拒绝删除时，只对受控非链接目标清除该属性并重试；不会绕过 ACL 或其他文件锁。仍然失败时返回 409，保留记录，并在后台记录具体原因。已完成的部分文件删除不会回滚，但后续重试可容忍缺失文件。不允许通过任意路径删除文件。

十六、CLI 与运行环境

CLI 命令：

research reparse PAPER_ID
research search "parallel trends"
research deep-read PAPER_ID
research deep-read PAPER_ID --focus identification
research usage

项目要求 Python 3.11 和现有 Conda 环境 econ-research，不应修改 Conda base 或系统 Python。推荐检查命令：

conda run -n econ-research pytest
conda run -n econ-research ruff check .
conda run -n econ-research research serve

主要配置包括 OPENAI_API_KEY、OPENAI_DEFAULT_MODEL、OPENAI_CARD_MODEL、OPENAI_DEEP_READ_MODEL、两种 reasoning effort、ECON_RESEARCH_DATA_DIR、ECON_RESEARCH_DB_PATH、ECON_RESEARCH_FORMULA_ENRICHMENT 和 ECON_RESEARCH_PADDLE_FORMULA_OCR。

macOS 使用 start-research.command，Windows 使用 start-research.cmd。两者默认补齐公式库，可用 --without-formula 跳过安装、--setup-only 准备环境。Windows 正常服务在前台输出，Ctrl+C 请求优雅停止；已有后台时可选 R 重启到当前窗口、S 停止、L 只读日志、Q 保持后台退出。独立 stop-research.cmd 会核对进程、拒绝活动上传并要求输入 STOP；它是终止进程的备用入口，不等同于 Ctrl+C，使用前须结束重解析、卡片和深读请求。关闭只读日志窗口不会停止服务。

十八、已知限制

- 搜索是 FTS5 词法搜索，不是语义搜索。
- 卡片还不能编辑、审批或批量导出。
- 标签尚未统一规范化。
- 深读只针对单篇论文。
- 没有跨论文比较工作区。
- 正文主要使用 Docling，不使用整篇 OCR。
- 表格目前以 Markdown 表格块保留，复杂跨页表格、布局关系和视觉样式仍可能需要人工核对。
- 公式 OCR 和旧 PDF 标题修复仍需人工核对；未验证公式会以非渲染代码形式保留，而不是被强行当作正确 LaTeX。
- 不能脱离原始 PDF 把生成内容视为最终事实。
- 没有用户账户和多用户权限。
- 没有 Zotero 集成。
- 只有 OpenAI 实现，没有通用多 Provider 网关。
- Windows CUDA 13 路径已实测；macOS、全新 CPU 环境和 CUDA 12.6 设备仍需原生验证。

新增功能应遵循以下顺序：

SQLiteRepository
    -> ResearchService
